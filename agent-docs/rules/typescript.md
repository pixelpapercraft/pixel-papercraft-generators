# TypeScript

## Prefer `type` aliases over `interface`

Declare object shapes and composition with `type` — express what `extends` would do as an `&` intersection. Reach for `interface` only for a capability unique to it: chiefly global declaration-merging (augmenting an existing interface across files).

**Why:** `interface` and `type` overlap for ordinary shapes, so a mixed use is just inconsistency; `interface` additionally merges silently when the same name is declared twice, so defaulting to `type` keeps shapes consistent and turns an accidental redeclaration into a compiler error instead of a silent merge.

## Guard a finite-union `switch` with `default: return <subject> satisfies never`

End every `switch` over a finite union (a string/number-literal union, or a discriminated union's tag) with `default: return <subject> satisfies never` — the `return` form, in `void` functions too. Omit it only for a `switch` over an open type (`string`, `number`) whose default is genuinely reachable.

**Why:** TypeScript's built-in exhaustiveness fires only when a missing case makes a value-returning function fall off its end returning a type the signature rejects; it goes silent for `void` returns, and in a nested `switch` when a non-exhaustive inner `switch` falls through into a later outer case that returns — swallowing the unhandled member with no error. An explicit `satisfies never` is narrowed to that member and errors regardless of control flow, nesting, or case order. Use the `return` form because the bare `<subject> satisfies never;` fails to compile in a value-returning function ("lacks ending return statement"), while the `return` form type-checks in both value-returning and `void` functions (`never` is assignable to every return type).

## Don't reach for the type-system escape hatches

Get a type right at its source rather than overriding the checker: don't use a type assertion (`x as T`, `as unknown as T`, `<T>x`), `any`, the non-null assertion `!`, or `@ts-ignore` / `@ts-expect-error`. Reach instead for boundary parsing that returns a precise type (this repo already uses `zod` for this), control-flow narrowing (`typeof`, `in`, a discriminant check), and data modelled so a wrong state can't be expressed. `as const` and `satisfies` are not escape hatches — they check without widening or asserting a type the value doesn't have — and stay allowed. Self-check: scan the code you write for `as`, `any`, `!`, and `@ts-`, and remove or justify each.

Exception: a type assertion (`as T` or `as unknown as T`) confined to a shared test fixture's own internals (never inside an individual test's own body) is acceptable when mocking a globally standardized, cross-vendor web-platform API — e.g. the Canvas 2D API — not a general third-party npm package, whose types are far more likely to drift. Applies only once the function-under-test's own parameter type has been narrowed first, to only the members it actually uses.

**Why:** every escape hatch tells the compiler to stop checking at the exact seam where a mistake goes invisible — `as` slips an unrelated type through, `any` disables checking transitively across everything it touches, `!` turns a real `null` into a crash far from its cause. The master stance makes the checker the first reviewer; silencing it there trades a compile error you'd see now for a production failure you won't. This includes `as unknown as T` in test mocks: build the mock so it structurally satisfies the real type instead — a factory that returns a complete fake object (every member implemented, `vi.fn()` where behavior doesn't matter for that test), or narrowing the function-under-test's parameter type to only the members it actually uses — rather than casting a partial object past the checker. The exception above holds because a standards-track browser API's shape carries near-zero risk of the silent breaking change this rule guards against — unlike an npm package's types, which a single maintainer can change at will — and because a full structural fake of a 50+ member DOM interface would itself become unreviewable test code, the worse failure mode.

## Annotate a literal with the named type it is built to satisfy

When you write an object, array, or function-bag literal whose purpose is to conform to an existing named type — it is passed to a parameter of that type, assigned to a field of it, or returned as it — declare that type on the binding: `const props: GeneratorProps = { … }`, or `const props = { … } satisfies GeneratorProps` when you must keep the literal's narrow inferred type. Don't leave it inferred and lean on the assignability check at the call site. This is not "annotate every `const`": skip values with no named contract to meet (`const count = 0`, a `.map` result); the trigger is that a named type for the value already exists. Self-check: for each un-annotated object or function literal you introduce, ask whether it is consumed as a named type — if so, name that type on its declaration.

**Why:** an un-annotated literal is checked only at its use, and only loosely — a literal loses freshness once bound to a variable, so a leftover or misspelled property (`baseHieght`) is silently accepted when that variable is later passed on, and a value never passed to a site that demands the full type is never checked at all. Annotating the binding moves the check to where the value is written: excess, missing, and misspelled properties error at the definition, and nested function parameters are contextually typed from the target, so a change to the named type's signature forces the literal's parameters to match instead of letting hand-written ones drift. The payoff the whole master stance is after — when the named type changes, every construction site fails deterministically at its definition, rather than surfacing a confusing error at a distant consumer, or no error at all.

## Type the expected value of a non-primitive test assertion with the matcher's generic argument

On a Vitest matcher that compares a non-primitive value — `toEqual`, `toStrictEqual`, `toMatchObject`, `toContainEqual`, `toContain`, or `toBe` on an object or array — supply the expected type as the matcher's type argument: `expect(region).toEqual<Rectangle>({ … })`. Prefer the named domain type; when none is exported (a third-party or anonymous inline type) or the subject's own declaration is the source of truth, derive it from the subject with `typeof` — `expect(placements).toEqual<typeof placements>([…])`. Skip it for primitive comparisons (`toBe("x")`, `toBe(2)`, `toBeNull()`, `toBeCloseTo(…)`). Self-check: for each object- or array-valued `expect(...)`, confirm the matcher carries a `<Type>`.

**Why:** left to inference, the matcher binds its generic to the expected value's _own_ type, so the checker only ever compares the literal against itself — never against the type the subject actually produces. The expected shape can then drift from what the code now returns and still compile, and the mismatch surfaces only when the suite is run — later and slower than a typecheck, the one signal these agents lean on before deploy. Supplying the type binds the expectation to it, so a shape change becomes a compile error at the assertion — the same deterministic signal the annotate-the-literal rule gives constructors, extended to the expectations that pin behaviour. Deriving it with `typeof <subject>` keeps that signal self-maintaining: change the subject's type and every expectation of it must move with it.

## Mock a module with `vi.mock(import("./path"), factory)`, written inline

Write the target of a Vitest module mock as an `import("./path")` expression, inline as `vi.mock`'s first argument — never a plain string path, and never a variable holding a pre-evaluated `import(...)`.

**Why:** a plain string path can't be tied to the target module's shape, so the factory's return type collapses to `Partial<unknown>` and TypeScript accepts any object back — including one with renamed or invented exports — so a mocked module can silently drift from the real one with no compile error. Passing a variable instead of the inline expression compiles for the same reason but fails at runtime for a different one: `vi.mock(...)` calls are hoisted by a compile-time transform to the top of the file so the mock is registered before anything else runs, and that transform moves only the call itself, not a variable declaration its argument depends on — so the variable is read before its `const` initializes, throwing `ReferenceError: Cannot access '<name>' before initialization`.
