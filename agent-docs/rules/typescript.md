# TypeScript

## Prefer `type` aliases over `interface`

Declare object shapes and composition with `type` — express what `extends` would do as an `&` intersection. Reach for `interface` only for a capability unique to it: chiefly global declaration-merging (augmenting an existing interface across files).

**Why:** `interface` and `type` overlap for ordinary shapes, so a mixed use is just inconsistency; `interface` additionally merges silently when the same name is declared twice, so defaulting to `type` keeps shapes consistent and turns an accidental redeclaration into a compiler error instead of a silent merge.

## Guard a finite-union `switch` with `default: return <subject> satisfies never`

End every `switch` over a finite union (a string/number-literal union, or a discriminated union's tag) with `default: return <subject> satisfies never` — the `return` form, in `void` functions too. Omit it only for a `switch` over an open type (`string`, `number`) whose default is genuinely reachable.

**Why:** TypeScript's built-in exhaustiveness fires only when a missing case makes a value-returning function fall off its end returning a type the signature rejects; it goes silent for `void` returns, and in a nested `switch` when a non-exhaustive inner `switch` falls through into a later outer case that returns — swallowing the unhandled member with no error. An explicit `satisfies never` is narrowed to that member and errors regardless of control flow, nesting, or case order. Use the `return` form because the bare `<subject> satisfies never;` fails to compile in a value-returning function ("lacks ending return statement"), while the `return` form type-checks in both value-returning and `void` functions (`never` is assignable to every return type).

## Don't reach for the type-system escape hatches

Get a type right at its source rather than overriding the checker: don't use a type assertion (`x as T`, `as unknown as T`, `<T>x`), `any`, the non-null assertion `!`, or `@ts-ignore` / `@ts-expect-error`. Reach instead for boundary parsing that returns a precise type (this repo already uses `zod` for this), control-flow narrowing (`typeof`, `in`, a discriminant check), and data modelled so a wrong state can't be expressed. `as const` and `satisfies` are not escape hatches — they check without widening or asserting a type the value doesn't have — and stay allowed. Self-check: scan the code you write for `as`, `any`, `!`, and `@ts-`, and remove or justify each.

**Why:** every escape hatch tells the compiler to stop checking at the exact seam where a mistake goes invisible — `as` slips an unrelated type through, `any` disables checking transitively across everything it touches, `!` turns a real `null` into a crash far from its cause. The master stance makes the checker the first reviewer; silencing it there trades a compile error you'd see now for a production failure you won't. To give a value a distinct (nominal) type without a cast, use the wrapper-object rule below.

## Model a nominal ("branded") type as a wrapper object, not a branded primitive

When a value needs its own type so a bare `string` or `number` can't be passed in its place (a rendered prompt vs. a raw task, a validated id vs. any string), define it as an object with one `readonly` field — `type Prompt = { readonly text: string }` — built with a plain object literal and read through that field. Don't use a branded-primitive intersection (`string & { readonly __brand: "Prompt" }`) or any phantom `__brand` / `_tag` field.

**Why:** a branded primitive has no values of its own, so it can only be produced by a type assertion (`rendered as Prompt`) — the escape hatch the rule above forbids, sitting at the one seam correctness depends on. A wrapper object is satisfied structurally by an ordinary literal, so it needs no assertion, while a bare primitive still fails to type-check against it: the same "can't pass the wrong thing" guarantee, expressed with a type any reader understands and the checker enforces without a cast. It is structurally forgeable (`{ text: raw }` also satisfies it), but that guards the realistic mistake — dropping the constructor and passing the raw primitive — without the type gymnastics a truly unforgeable brand demands.

## Convert a typed external boundary with a transformer, not by widening to `unknown` and re-parsing

When an external system (an SDK, a typed library) already hands you a static type, convert it to your domain type with a typed transformer — `(e: SdkEvent) => DomainEvent` — so the compiler checks the mapping against the source. Don't widen it to `unknown` (`parse(raw: unknown)` fed an already-typed value) and rebuild your type with a runtime parser. Reserve parsing-from-`unknown` for genuinely untyped or untrusted input: the wire, disk, process input, and the individual fields a typed source itself declares `any`/`unknown`. Where the source type is already exactly your domain type, adopt it directly with a type **alias**; where you deliberately want a different shape, that is a **projection** — define your domain type *explicitly* and map into it with the transformer, rather than welding it to the source with `Pick`/`Omit` or hand-rolling a parallel shape fed from `unknown`. Do this as soon as the source's types are installable — add the dependency and adopt/transform now, not after a later refactor.

**Why:** widening a typed value to `unknown` discards the compiler's ability to check your mapping against the source shape — if the source restructures a field, a runtime parser silently yields a fallback while a transformer fails to compile, so drift surfaces at build time instead of as a quiet runtime hole. A transformer also composes with the finite-union `switch` guard above: when the source's union grows, `satisfies never` forces you to handle the new member. Parsing from `unknown` is for data with no trustworthy type to retain; a decoupling goal doesn't justify discarding one you already have — decouple the *runtime* behind an interface (so tests can fake it) while keeping the source's *types* as your domain vocabulary. An explicit projection plus a typed transformer keeps that safety while leaving the domain type readable and decoupled — the transformer's typed *input* is the compiler link, so the domain shape needn't mirror the source's. And a stub shape parsed from `unknown` while the typed source sits one dependency away has no compiler link at all: it drifts silently until a future refactor tears it out, whereas adopting or transforming the real type now makes drift a build error today and leaves nothing to remove.

## Annotate a literal with the named type it is built to satisfy

When you write an object, array, or function-bag literal whose purpose is to conform to an existing named type — it is passed to a parameter of that type, assigned to a field of it, or returned as it — declare that type on the binding: `const props: GeneratorProps = { … }`, or `const props = { … } satisfies GeneratorProps` when you must keep the literal's narrow inferred type. Don't leave it inferred and lean on the assignability check at the call site. This is not "annotate every `const`": skip values with no named contract to meet (`const count = 0`, a `.map` result); the trigger is that a named type for the value already exists. Self-check: for each un-annotated object or function literal you introduce, ask whether it is consumed as a named type — if so, name that type on its declaration.

**Why:** an un-annotated literal is checked only at its use, and only loosely — a literal loses freshness once bound to a variable, so a leftover or misspelled property (`baseHieght`) is silently accepted when that variable is later passed on, and a value never passed to a site that demands the full type is never checked at all. Annotating the binding moves the check to where the value is written: excess, missing, and misspelled properties error at the definition, and nested function parameters are contextually typed from the target, so a change to the named type's signature forces the literal's parameters to match instead of letting hand-written ones drift. The payoff the whole master stance is after — when the named type changes, every construction site fails deterministically at its definition, rather than surfacing a confusing error at a distant consumer, or no error at all.

## Type the expected value of a non-primitive test assertion with the matcher's generic argument

On a Vitest matcher that compares a non-primitive value — `toEqual`, `toStrictEqual`, `toMatchObject`, `toContainEqual`, `toContain`, or `toBe` on an object or array — supply the expected type as the matcher's type argument: `expect(region).toEqual<Rectangle>({ … })`. Prefer the named domain type; when none is exported (a third-party or anonymous inline type) or the subject's own declaration is the source of truth, derive it from the subject with `typeof` — `expect(placements).toEqual<typeof placements>([…])`. Skip it for primitive comparisons (`toBe("x")`, `toBe(2)`, `toBeNull()`, `toBeCloseTo(…)`). Self-check: for each object- or array-valued `expect(...)`, confirm the matcher carries a `<Type>`.

**Why:** left to inference, the matcher binds its generic to the expected value's *own* type, so the checker only ever compares the literal against itself — never against the type the subject actually produces. The expected shape can then drift from what the code now returns and still compile, and the mismatch surfaces only when the suite is run — later and slower than a typecheck, the one signal these agents lean on before deploy. Supplying the type binds the expectation to it, so a shape change becomes a compile error at the assertion — the same deterministic signal the annotate-the-literal rule gives constructors, extended to the expectations that pin behaviour. Deriving it with `typeof <subject>` keeps that signal self-maintaining: change the subject's type and every expectation of it must move with it.
